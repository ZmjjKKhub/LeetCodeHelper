## 0. 设计约束

优先级最高。任何功能取舍都服从这一节。

| # | 约束 | 说明 |
|---|---|---|
| C1 | **录入摩擦 = 生死线** | A/B 类题记录 ≤ 20 秒（3 次点击内完成），C 类卡片 ≤ 3 分钟。任何需要打字超过 5 个字段的默认流程都要重新设计 |
| C2 | **单人本地** | 不做 auth、不做用户表、不做 RBAC。数据放本地 SQLite 单文件 |
| C3 | **离线可用** | 不依赖任何外部 API 才能跑起来 |
| C4 | **系统不碰代码执行** | 做题全部在 LeetCode 平台上完成。本系统只负责规划刷题路径与复盘，不内置编译器、判题器或任何执行环境 |
| C5 | **单进程运行** | `uv run app.py` 后浏览器打开 localhost 即可用——前端构建产物由 FastAPI 静态托管，运行时只有一个进程。不要 docker-compose。开发前端时可以另起 Vite dev server，但那只是开发期便利，不是运行前提 |
| C6 | **数据可搬走** | 全量 JSON 导出/导入。换电脑、备份、迁移都靠它 |

### C4 的边界说明

系统里出现的编辑器（P6 模板默写）只是带语法高亮的文本框，提交后用 `difflib` 做文本比对，**不执行代码**。P6 的限时盲测是「系统出题 + 计时」，你去 LeetCode 上做，回来点通过/未通过。两者都不违反 C4。

## 1. 技术选型

已定，不再讨论。

| 层 | 选择 |
|---|---|
| 后端 | Python 3.12 + FastAPI |
| 数据库 | SQLite + SQLModel |
| 前端 | React + TypeScript + Vite（v2 起；v1 是 Jinja2 + HTMX，已废弃） |
| 样式 | Tailwind CSS（随 Vite 构建，产物自包含） |
| 迁移 | Alembic |
| 编辑器组件 | CodeMirror 6，同样本地化，仅用于高亮，不执行代码 |
| 测试 | pytest + 内存 SQLite |

**明确不用**：Docker、Redis、Celery、任何后台任务队列、任何服务端模板引擎。

**前端依赖一律不走 CDN，字体也不走。** C3 要求离线可用。所有依赖在构建期打进产物，运行时不发起任何第三方请求——包括 Google Fonts。测试里有一条断言禁止产物引用外部域名。

> **v1 → v2 的技术栈变更（2026-09-02）。** v1 用 Jinja2 + HTMX + Alpine，理由是「表单密集场景，避免前后端两套状态」。真实使用一周后改为 React：一是界面需要认真设计，二是后续的统计（趋势图 + 热力图）、计划（拖拽排期）、检测（倒计时 + diff）三类页面在 HTMX 下写起来别扭。
> 换的时机选在现在，是因为此刻只有 4 个模板要扔，等 Phase 2–5 做完就是 12 个以上。
> **代价被 §2 的两条分层纪律限制住了**：`services/` 不碰 `Request`、数据访问只在 `repositories/`，所以爆炸半径只有 Web 层 662 行 + 52 个 Web 测试，另外 132 个测试原样保留。

## 2. 架构与目录

单进程 FastAPI。分层的唯一目的是让第 5 节的业务规则能脱离 HTTP 被测试。

```
app.py                        # 入口：建表检查 + 启动浏览器
leetcode_helper/
  models.py                   # SQLModel 定义
  db.py                       # engine / session
  repositories/               # 唯一碰 DB 的地方
  services/
    scheduling.py             # R1 R2 —— 纯函数，不碰 session
    curriculum.py             # 回炉逻辑（section 级）
    planning.py               # R3 R4
    suggestions.py            # R5
    topics.py                 # topic.yaml 加载与卡片 schema
    export.py                 # 全量 JSON 导出/导入
  api/                        # FastAPI 路由，只返回 JSON
  seed/                       # 种子导入脚本
frontend/                     # React + TypeScript + Vite
  src/
    pages/                    # 今日 / 历史 / 计划 / 模板库 / 触发器 / 检测 / 统计
    components/
    api/                      # 与 /api 对接的类型与请求
  dist/                       # 构建产物，由 FastAPI 静态托管（不入库）
data/
  topics/
    sliding-window/
      topic.yaml
      problems.yaml
      templates.yaml
      plan_default.yaml
tests/
```

### 分层纪律（两条）

1. **`services/` 里的函数签名一律「数据进、数据出」**，不接受 `Session`，不接受 `Request`，不读全局单例。R2 的四个 case 因此可以纯内存测试。
2. **所有数据访问集中在 `repositories/`**。

这两条纪律同时是产品化的唯一投资：将来若要上线，加 `user_id` 就是一次 Alembic 迁移 + repository 层加过滤条件，业务逻辑一行不动。现在**不写任何多租户代码**。

## 3. Topic 抽象

系统面向「一次刷一个专题，且能换专题」。滑动窗口是第一个专题；二分、单调栈、DP 将来各是一个 topic，历史卡片全部保留可查。

复盘卡片的字段是**专题特有**的：滑窗要问「单调性 / 维护量 / 收缩条件 / 统计时机」，二分要问「check 函数怎么写 / 边界取 `l=mid` 还是 `l=mid+1`」，单调栈要问「栈里存下标还是值 / 弹栈时机」。因此卡片字段由 topic 的 YAML 驱动，表单动态渲染。

### 3.1 `topic.yaml`

```yaml
code: sliding-window
name: 滑动窗口
time_limits: { easy: 480, medium: 1200, hard: 2100 }   # 秒
card_fields:
  - { key: trigger_feature,  label: 触发特征, type: text }
  - { key: monotonicity,     label: 单调性,   type: text }
  - { key: maintained_value, label: 维护量,   type: choice, options: [sum, Counter, 不同元素个数, 其他] }
  - { key: shrink_condition, label: 收缩条件, type: text }
  - { key: count_timing,     label: 统计时机, type: choice, options: [入窗后, 出窗循环内, 出窗循环外] }
```

`type` 支持 `text` 与 `choice` 两种，够用即可，不做更复杂的字段类型系统。

### 3.2 加新专题的成本

新建一个 `data/topics/<code>/` 目录，放四个 YAML（topic / problems / templates / plan_default），跑一次种子导入。**不改代码，不改 schema。**

### 3.3 Topic 在 UI 中的位置

P5 触发器库、P7 热力图、P3 计划默认按**当前 topic** 过滤，顶部留一个 topic 切换器。

## 4. 数据模型

### 4.1 静态数据

```
Topic
  id            PK
  code          str UNIQUE      # "sliding-window"
  name          str
  config_json   text            # topic.yaml 原文，含 time_limits / card_fields
  is_active     bool

Problem
  id                PK
  topic_id          FK
  lc_id             int         # 力扣题号
  title             str
  url               str
  difficulty        enum        # easy / medium / hard（取自 LeetCode）
  section           str         # "§2.2"
  section_name      str
  is_starred        bool        # 高频面试题
  is_premium        bool
  is_optional       bool        # 选做 / 进阶
  default_template  str | None  # 预期使用的模板 code

Template
  id              PK
  topic_id        FK
  code            str          # "A".."F"，唯一约束为 (topic_id, code)
  name            str
  language        str
  content         text
  pitfalls        text
  trigger_signal  text
  current_version int
  updated_at      datetime

TemplateVersion
  id                       PK
  template_id              FK
  version                  int
  content                  text
  change_note              str          # 必填
  triggered_by_problem_id  FK | None    # 是哪道题让你改的模板
  created_at               datetime
```

> `triggered_by_problem_id` 是系统的核心设计，务必实现。它把「模板演进史」和「做题史」绑在一起。

**难度不再使用灵神难度分**（拿不到）。改用 LeetCode 的 easy/medium/hard，限时由它经 `topic.config_json.time_limits` 推导。

### 4.2 计划

```
Plan
  id, topic_id, name, start_date, status(active/archived)

PlanDay
  id, plan_id, day_index, planned_date, actual_date | None
  phase   str        # "阶段三 · 求最短+求个数"
  theme   text       # 当天要抽象出的东西
  status  enum       # pending / done / skipped / postponed

PlanItem
  id, plan_day_id, problem_id, sort_order
  status  enum       # pending / done / deferred

PlanSuggestion
  id, plan_id, week_start, kind, payload_json
  status  enum       # pending / accepted / ignored
  created_at
```

`Plan` 不含 `days_per_week` / `minutes_per_day` —— 没有任何规则用到它们。

### 4.3 做题与复盘

```
Attempt
  id              PK
  problem_id      FK
  attempt_date    date
  kind            enum        # new / review
  review_task_id  FK | None
  duration_bucket enum        # within / over / unsolved   ← 必填
  duration_sec    int | None  # 可选精确用时（仅当使用了计时器）
  time_limit_sec  int         # 当时生效的限时，快照
  submit_count    int         # 默认 1
  mark            enum        # A / B / C
  used_template   str | None
  created_at
```

**不存 `first_try_ac` 字段。** 它是派生量：`first_try_ac = (submit_count == 1 and duration_bucket != unsolved)`。P1 面板里没有「是否 AC」这个勾选框，存一个没有独立输入来源的字段只会带来不一致。R5 与 P7 的「一次 AC 率」按此式现算。

**`Attempt` 存原始信号，不存压缩后的结论。** 将来喂给 FSRS 的 rating 由这些字段现算——提前压成一个 0–5 的数，信息就拿不回来了。

```
ReviewCard                     # 跨专题公共字段
  id             PK
  problem_id     FK UNIQUE
  topic_id       FK
  blocker        text          # 我的卡点（一行）
  trigger_see    str           # 看到「X」
  trigger_use    str           # → 用「Y」
  template_id    FK | None
  needs_rewrite  bool          # R2 置位：卡片没写对
  created_at, updated_at

ReviewCardField                # 专题特有字段
  id        PK
  card_id   FK
  field_key str               # 对应 topic.yaml 的 card_fields[].key
  value     text
  UNIQUE (card_id, field_key)
```

`trigger_see` / `trigger_use` 拆成两列，P5 触发器库直接 SELECT 两列成表，无需解析字符串。

```
ReviewTask
  id, problem_id FK, due_date date
  round      int        # 第几轮
  status     enum       # pending / passed / failed / skipped
  attempt_id FK | None
  created_at

MemoryState                    # 只写不读，为 v2 FSRS 蓄数据
  problem_id       PK
  stability        float
  difficulty_param float
  reps             int
  lapses           int
  last_review      date

DrillRecord
  id, drill_type(template_writing / blind_retest)
  target_id                    # template_id 或 problem_id
  passed bool, diff_result text, duration_sec, created_at
```

**不设 `DailyLog` 表。** 几千行数据的聚合查询是微秒级，落库只是维护成本。P7 的统计一律按需聚合。

## 5. 核心业务规则

最重要的一节。逐条实现为 `services/` 下的独立纯函数并配单元测试。

### R1 · 复习队列生成

做题打标后，自动生成 `ReviewTask`，`due_date` 基于 `attempt_date` 计算：

| 标记 | 生成的复习轮次 |
|---|---|
| A | 不生成 |
| B | D+3、D+14（2 轮） |
| C | D+1、D+3、D+7、D+14（4 轮） |

### R2 · 复习结果处理

系统的灵魂，不要简化。

pass/fail 判定直接由 `duration_bucket` 给出：`within` = passed，`over` 或 `unsolved` = failed。限时来自 `topic.config_json.time_limits[problem.difficulty]`。

```
if passed:
    标记本轮 passed，保留后续轮次不变

if failed:
    case round == 1:
        整条队列重置 —— 删除该题所有 pending 轮次，
        以今天为基准重新生成 D+1/D+3/D+7/D+14，
        并把 ReviewCard.needs_rewrite 置为 true

    case 中间轮次（不是第一轮，也不是最后一轮）:
        本轮 failed，回退一轮 —— 在 (今天 + back_gap) 插入一次重做，
        该次重做的 round 仍记为当前 round，
        后续所有 pending 轮次的 due_date 顺推 back_gap 天

    case 最后一轮:
        C 类 → 触发回炉（见 R7）
        B 类 → 降级为 C：删除该题所有 pending 轮次，
               以今天为基准按 C 类重新生成四轮，mark 不改写
```

轮次定义（`OFFSETS` 相对基准日，`back_gap = OFFSETS[i] - OFFSETS[i-1]`）：

| mark | OFFSETS | round 2 的 back_gap | round 3 的 back_gap |
|---|---|---|---|
| C | `[1, 3, 7, 14]` | 2 | 4 |
| B | `[3, 14]` | — （round 2 即最后一轮） | — |

C 类只有 round 2 和 round 3 属于「中间轮次」；B 类没有中间轮次。

### R3 · 每日任务组装

```
今日任务 = [到期的 ReviewTask（按 round 降序，越老的越先做）]
         + [今天 PlanDay 的 PlanItem]
```

UI 上复习队列必须排在新题**前面**，并且默认展开——脑子最清醒时做最难的事。

### R4 · 断更与顺延

- 某天 PlanDay 未完成 → **整体顺延**，后续所有 PlanDay 的 `planned_date` +1 天。不标记为「失败」，不产生补做积压。
- 连续 3 天未完成 → 首页红色提示：「建议回退到 [上一阶段名]，重刷该阶段的 C 类题」，并提供一键生成回退计划的按钮。
- 复习任务**不顺延**。逾期就是逾期，逾期任务在首页单独一栏高亮。

### R5 · 计划自适应建议

每周结束时计算，生成 `PlanSuggestion` 供用户确认：

| 条件 | 建议 |
|---|---|
| 周 C 类占比 > 40% | 下周新题量 −30%，腾出的时间给复习队列 |
| 周 C 类占比 < 10% 且模板默写连续 2 周满分 | 加入本阶段的「选做/进阶」题 |
| 周一次 AC 率 < 30% 且持续 3 天 | 当前阶段难度不匹配，建议回退 |
| 某 section 的 C 类题占该 section 题量 > 50% | 该小节需整体重刷 |

**必须是「生成建议卡片 + 用户点击接受/忽略」，绝不自动修改计划。** 自动改计划会让用户失去掌控感。

### R6 · 模板演进链路

- `Attempt` 记录 `used_template`
- 模板详情页反查：使用过该模板的题目列表（按 mark 分组，C 类高亮）
- 编辑模板时**必须**填 `change_note`，可选关联 `triggered_by_problem_id`
- 模板页展示版本时间线，任意两版可 diff（`difflib.unified_diff` 渲染）

### R7 · 回炉（section 级）

由 R2 的 `round == 4` failed 触发：

1. 该题标记 relearn
2. 该题所属 section 下所有 `mark == C` 的题重新入队（D+1 起）
3. 首页提示：「§X.X 未掌握，建议重刷本小节」

**回炉放在 `services/curriculum.py`，不放在 Scheduler 里。** 它是课程编排规则，与单题记忆调度是两件事；将来换 FSRS 时它必须原样保留。

## 6. 调度器抽象

v1 的固定间隔表本质是查找表。现在实现它，但把接口留出来，同时开始积累数据，等有了真实样本再考虑换成 FSRS——**有数据支撑地**换，而不是一上来就调一个没法验证的模型。

```python
class Scheduler(Protocol):
    def on_new_attempt(self, attempt) -> list[ReviewTask]: ...          # R1
    def on_review_result(self, task, attempt) -> SchedulerAction: ...   # R2
```

- `FixedTableScheduler` 是当前**唯一**实现，逐条照搬 R1/R2。
- 每次复习额外调用 `memory.record(attempt)` 更新 `MemoryState`。**该状态不参与任何决策**，纯粹积累数据。
- 攒够一两百条复习记录后写 `FsrsScheduler`，用真实数据回测留存率曲线再切换。

FSRS 的冷启动问题（默认参数是拿别人的记忆数据训的，对「能否 20 分钟内 AC」未必适用）就是推迟它的理由。

## 7. 页面清单

### P1 · 今日（首页）

三块自上而下：

1. **逾期复习**（红色，如有）
2. **今日复习队列**：题目 + 第几轮 + 限时，每条一个「开始」按钮
3. **今日新题**：题目 + 难度 + 所属小节 + 当天主题

**空排期兜底**：当天没有 `PlanDay`（计划已排完、还没排、或断更后回来），第 3 块不显示空白，改为展示「该 topic 下所有未做题目」的列表，按 section 分组，可直接录入。这条兜底同时覆盖「临时想加练一题」的场景。走兜底录入的 `Attempt` 照常 `kind = new`，只是不关联 `PlanItem`。

**做题面板**（点击任一题展开，全系统最需要打磨的交互）：

```
提交次数  [-] 2 [+]                    ← 默认 1
用时      (限时内) (超时) (没做出来)     ← duration_bucket，必填
标记      (A) (B) (C)
模板      [ A B C D E F 无 ]            ← 默认取 problem.default_template
                                        [ 保存 ]  [ 计时 ]
```

四行，三次点击可完成（用时 + 标记 + 保存）。这才是 C1 说的 20 秒。

**不做常驻计时器作为默认路径。** 做题时浏览器标签页在 LeetCode 上，不在本系统上；后台标签页的计时器一旦忘记停止，数据就是错的，而错误的用时会污染将来喂给 FSRS 的信号。「计时」是可选入口，用于 P6 盲测这类需要精确用时的场景，写入 `duration_sec`。

点 A 或 B → 直接保存，流程结束。点 C → 保存后跳转卡片填写页。

### P2 · 复盘卡片

表单按当前 topic 的 `card_fields` **动态渲染**：`type: choice` 渲染成单选按钮，`type: text` 渲染成文本框。公共字段（blocker、trigger_see/trigger_use、template_id）固定在表单里。

- `trigger` 做成「看到 [____] → 用 [____]」两个输入框
- 提供「从同 section 的历史卡片复制」按钮，降低填写成本
- `needs_rewrite == true` 的卡片在列表里高亮，提示重写

### P3 · 计划

- 表格视图：Day / 日期 / 阶段 / 题目列表 / 状态
- 支持：整体顺延 N 天、某天增删题目、批量把某小节的题移到后面、手动插入题目
- 顶部：进度条 + 当前阶段 + 距离下个验收题还有几天
- 展示待确认的 `PlanSuggestion` 卡片（R5）

### P4 · 模板库

- 模板卡片列表 → 详情页
- 详情页：代码（CodeMirror 高亮）、易错点、触发信号、**使用该模板的题目反查列表**、版本时间线
- 编辑 → 强制填 `change_note` → 生成新 `TemplateVersion`
- 任意两版 diff

### P5 · 触发器库

面试前唯一要看的页面。聚合所有 `ReviewCard` 的 `trigger_see` / `trigger_use`，按 section 分组：

| 看到什么特征 | 用什么方法 | 来源题 |
|---|---|---|

支持搜索、导出 Markdown。

### P6 · 检测

- **模板默写**：随机抽一个模板 → 空白编辑器 → 提交 → 与当前版本 `difflib` 比对 → 记 `DrillRecord`。不执行代码。
- **限时盲测**：从指定范围（本周 / 某 section / 全部 C 类）随机抽 N 题，系统倒计时，你去 LeetCode 上做，逐题回来记录通过与否。
- **口述检查清单**：给定题目，展示该 topic 的 `card_fields` 作为必答问题，自评打勾。

### P7 · 统计

- 周报表：新题数 / 一次 AC 率 / C 类占比 / 总时长

  总时长的估算规则（`duration_sec` 非空时直接用它，否则按 bucket 折算）：

  | bucket | 估算值 |
  |---|---|
  | `within` | `0.6 × time_limit_sec` |
  | `over` | `1.5 × time_limit_sec` |
  | `unsolved` | `1.5 × time_limit_sec` |

  UI 上该数字必须标注「估算」，避免被当成精确统计。

- 按 section 的掌握度热力图（用 C 类占比着色）
- 一次 AC 率与 C 类占比的双折线趋势图
- 过关判定：C 类占比 < 15% 且模板默写连续 2 周满分 → 显示「本专题可结业」

### P8 · 设置 / 数据

- 全量 JSON 导出与导入（C6）
- topic 切换器
- 限时参数覆盖

### 9.2 其余

- `templates.yaml`：各模板的初始 `content` / `pitfalls` / `trigger_signal`（用户提供，已有现成代码）
- `plan_default.yaml`：排期，每天 `problems` + `phase` + `theme`（用户提供）。Phase 1 只需 4 天 × 3 题的极简版本，用来把今日页喂上真实内容；Phase 1.5 再替换为完整排期（导入按 `day_index` upsert，不需重建库）
- `topic.yaml`：见 §3.1

### 9.3 导入脚本

按 `lc_id` upsert，支持增量导入——Phase 1.5 追加剩余题目时不需要重建库。

**导入时校验**（校验失败即中止，不写库）：

- `lc_id` 在同一 topic 内唯一
- `section` 非空
- `difficulty` 属于 {easy, medium, hard}
- `default_template` 必须存在于该 topic 的 `templates.yaml`
- `plan_default.yaml` 引用的 `lc_id` 必须存在于 `problems.yaml`
- `card_fields[].key` 唯一，`type` 属于 {text, choice}，`choice` 必须有非空 `options`

## 11. 实现提示

1. **先落 schema 再写业务**：第一步只做 `models.py` + 迁移 + seed 脚本，跑通后再往下。
2. **所有日期计算用 `date` 不用 `datetime`**，避免时区问题。
3. **HTMX 局部刷新**：做题面板保存后只刷新那一行，不整页重载。
4. **不引入后台任务队列**。每日汇总、复习到期判定全部在请求时惰性计算，或用启动时的一次性检查。
5. **`services/` 的函数不接受 `Session`**。见 §2 的分层纪律。
